## 2. Findings

### F01 — Production price freshness and sitemap `lastmod` are stale

**Classification:** verified defect.  
**Severity:** Critical.  
**Why Critical:** current prices are the primary organic landing-page content and the product's stated competitive signal. The defect is not merely metadata: the stale timestamp and snapshot are embedded in the visible HTML.

#### Evidence

The source snapshot used by static generation is dated 2026-08-31:

```json
// app/data/catalog-prices.json:1-5
{
  "fetchedAt": "2026-08-31T13:11:51.946Z",
  "sourceName": "فولاد ایرانیان",
  "sourceHome": "https://www.fooladiranian.com/",
  "taxRate": 0.1,
```

The static generator derives catalog `lastmod` from that snapshot and reads the committed JSON during each build:

```js
// scripts/lib/prerender-pipeline.mjs:425-429
for (const group of productGroups) {
  const catalog = await loadGroupCatalog(group.id);
  const lastmod = catalog.fetchedAt.slice(0, 10);
  const heroPreload = buildHeroPreloadTag(group);

// scripts/lib/prerender-pipeline.mjs:691-699
const [templateHtml, snapshotRaw] = await Promise.all([
  readFile(resolve(distDir, "index.html"), "utf8"),
  readFile(resolve(dataDir, "catalog-prices.json"), "utf8"),
]);
const snapshot = JSON.parse(snapshotRaw);
primeCatalogSnapshot(snapshot);
```

The current workflow does not commit every four hours. It explicitly never writes the repository and runs hourly during a daytime window:

```yaml
# .github/workflows/price-refresh.yml:1-18
name: Refresh prices (Cloudflare relay)
# ... it never reads or writes app/data, never runs git add/commit/push ...
on:
  schedule:
    # شنبه تا پنجشنبه، هر ساعت از 06:00 تا 21:00 به وقت تهران
    - cron: "0 6-21 * * 0-4,6"
      timezone: "Asia/Tehran"
permissions: {}
```

The workflow posts to a Worker (`.github/workflows/price-refresh.yml:44-48`). The Worker stores the snapshot and invokes a Pages deploy hook only when `DEPLOY_HOOK_URL` exists (`workers/price-refresh/worker.mjs:54-86`). During a Pages build, `scripts/pull-price-data.mjs:4-17` replaces the committed file only if `PRICE_DATA_ENDPOINT` is configured; otherwise it deliberately builds the repository copy.

Live and local rendered evidence agreed:

```text
Audit date:                                      2026-09-04
dist/rebar/ribbed/index.html fetchedAt:          2026-08-31T13:11:51.946Z
https://fouladbonyan.com/rebar/ribbed/ fetchedAt: 2026-08-31T13:11:51.946Z
live sitemap URL count:                          66
live sitemap lastmod=2026-08-31:                 53 URLs
live sitemap crawl:                              66/66 returned HTTP 200
```

The 53 entries are the home page plus 52 price routes. The remaining static dates were 1 URL at 2026-08-11, 5 at 2026-07-29, and 7 at 2026-08-17. Thus the sitemap is internally consistent with the rendered artifact, but both fail the expected refresh cadence.

Google says sitemap `lastmod` should represent the last significant page modification and is used only when it is consistently and verifiably accurate: [Build and submit a sitemap](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap).

#### Mechanism of harm

- **Render/rank:** users and crawlers receive stale visible prices and stale “آخرین دریافت داده” information.
- **Crawl:** the sitemap supplies no recent change signal for price routes, so it cannot help discovery of fresh snapshots.
- **Trust/conversion:** the page contradicts the product promise of current market-reference data.

The repository alone cannot identify whether ingestion, KV storage, deploy-hook invocation, Pages build configuration, or deployment failed. That root-cause step belongs under “Requires external data.”

#### Proposed fix

Restore and monitor the actual relay → KV → deploy hook → Pages build → `PRICE_DATA_ENDPOINT` path. Add a build/deploy freshness gate based on a defined business SLA; do not silently publish a stale repository snapshot as if current. Preserve the atomic complete-snapshot rule in `CONTEXT.md:19-21` and do not weaken validation.

#### Verification after implementation

1. Capture a successful GitHub Actions run, Worker `/status`, deploy-hook response, and Pages deployment ID for one snapshot.
2. Fetch a live price route and assert its embedded `fetchedAt` equals the published Worker snapshot.
3. Assert all 53 freshness-dependent sitemap entries carry the matching modification date.
4. Re-crawl all sitemap URLs and require one-hop-or-less 200 responses.
5. Add an alert for snapshots older than the agreed SLA; test the alert with a controlled stale fixture.

### F02 — Market widget causes a full-viewport layout shift after category auto-scroll

**Classification:** verified defect.  
**Severity:** High.

#### Evidence

Every catalog route automatically scrolls to the price workspace after hydration:

```tsx
// app/App.tsx:56-62
const didAutoScrollCategoryRoute = useRef(false);

useEffect(() => {
  if (!workspace.isCategoryRoute || didAutoScrollCategoryRoute.current) return;
  didAutoScrollCategoryRoute.current = true;
  scrollToPriceWorkspace();
}, [workspace.isCategoryRoute]);
```

At the same time, the market section begins as a short status rail, fetches asynchronously, and replaces it with a heading, card grid, and timestamp:

```tsx
// app/use-market-prices.ts:80-95
useEffect(() => {
  const load = async () => {
    const response = await fetch(MARKET_PRICES_URL, { cache: "no-store" });
    // ...
    setState({ status: "ready", data, isStale: isMarketPriceDataStale(data) });
  };

// app/MarketPrices.tsx:79-92,115-123
{state.status === "ready" ? (
  <>
    <div className="section-heading market-prices-heading">...</div>
    <div className="market-prices-grid">
      {state.data.items.map((item) => <MarketPriceCard ... />)}
    </div>
  </>
) : null}
{state.status === "loading" ? (
  <div className="market-status-rail" role="status" ...>...</div>
) : null}
```

Chrome 152.0.7977.83 CDP, 390 × 844 CSS px at DPR 2, Android/Pixel 6a user agent, 4× CPU slowdown, 150 ms latency, 1.6 Mbps downstream, cache disabled, three interleaved runs against the live `/rebar/ribbed/` page:

```text
Normal API response:   CLS 1.007109, 1.007109, 1.007109
Blocked market API:    CLS 0.007109, 0.007109, 0.007109

Normal shift sources:
  ~5198 ms  value 0.007109  DIV.shell, button.nav-toggle
  ~5336 ms  value 1.000000  DIV.shell  (scrollY ≈ 1982)
Blocked API scrollY after load: ≈ 1046
```

This A/B isolates the large shift to the successful widget expansion; disabling LightPillar did not change the 1.007 CLS. The 1.0 jump is consistent with content above the auto-scrolled target growing after the browser has moved the viewport. For context, Google's “good” CLS threshold is 0.1 or less at the 75th percentile: [Web Vitals](https://web.dev/articles/vitals).

#### Mechanism of harm

- **Render/UX:** the user's viewport jumps roughly one viewport after they land at the price workspace.
- **Rank:** CLS is a Core Web Vital used within Google's page-experience systems, while relevance remains primary: [Page experience](https://developers.google.com/search/docs/appearance/page-experience).

#### Proposed fix

Give the loading state a stable reserved footprint/skeleton equal to the ready state, move the optional market context below the price target, or coordinate the automatic scroll only after layout is stable. The smallest safe solution should preserve the primary price content and avoid hiding failures.

#### Verification after implementation

Repeat at least three interleaved runs on home, family, and subcategory templates under the same profile; require lab CLS ≤ 0.1 with success, failure, slow, and blocked API states. Check mobile, tablet, and desktop visually. Then confirm field CLS in CrUX/Search Console after enough traffic accrues.

### F03 — Faceted filter URLs are unnecessarily exposed to crawlers

**Classification:** deviation from documented best practice.  
**Severity:** Medium.

#### Evidence

The mega menu intentionally emits ordinary anchors carrying factory and size queries:

```tsx
// app/MegaMenu.tsx:20-26,36-41,66-86
// A factory or size has no page of its own ... with the pick carried as a
// `?factory=`/`?size=` query param ... still a real navigation
const filterHref = (param: "factory" | "size", value: string) =>
  `${filterBaseHref}?${param}=${encodeURIComponent(value)}`;

<a href={filterHref("factory", factory)}>...</a>
<a href={filterHref("size", size)}>...</a>
```

The client reads these values only after navigation (`app/catalog-search-coordinator.ts:299-312`). Rendered-output inventory:

```text
internal query-link occurrences: 922
unique query URLs:                145
rel=nofollow:                     0
median query links/page:          17
maximum query links/page:         32

unique variants by base family:
angle 19; beam 17; channel 16; rebar 29; pipe 5;
profile 32; sheet 18; wire 9
```

A representative live URL returned 200 while canonicalizing to the clean page:

```text
GET /rebar/ribbed/?factory=ذوب%20آهن  -> 200
canonical                            -> https://fouladbonyan.com/rebar/ribbed/
```

The canonical is correct but does not prevent discovery or crawling. Google's faceted-navigation documentation states that parameter combinations can create very large URL spaces and waste crawl resources; it recommends preventing crawl when faceted URLs need not be indexed: [Faceted navigation](https://developers.google.com/crawling/docs/faceted-navigation).

#### Mechanism of harm

- **Crawl:** Googlebot can follow 145 currently enumerated variants and any future combinations, despite all consolidating to clean canonical pages.
- **Index:** self-consistent canonicals reduce duplicate indexing risk, but canonical is a hint rather than a crawl-control mechanism.

There is no evidence in the repository that these filter states deserve separate search results, and there is no unique server-rendered metadata for them.

#### Proposed fix

Keep clean subcategory links as ordinary anchors, but make non-indexable filter controls client-side buttons/state or a fragment-based state when appropriate. If real URLs must remain, narrowly disallow only the known `factory` and `size` parameter patterns in `robots.txt`. Do not blanket-block legitimate clean catalog routes.

#### Verification after implementation

Build and assert zero `?factory=`/`?size=` anchors in `dist`, all 52 price pages remain reachable from clean links, and filter behavior works with JS. After deployment, use verified Googlebot logs and Search Console crawl/index data to confirm parameter crawling declines without harming clean route discovery.

### F04 — Price-page metadata and visible copy are highly templated

**Classification:** documented best-practice deviation plus judgment call.  
**Severity:** Medium.  
**Confidence note:** the repetition metrics are verified; any ranking effect is inferred and cannot be quantified from the repository.

#### Evidence

All 44 subcategory descriptors use the same literal sentence templates:

```js
// scripts/lib/prerender-pipeline.mjs:485-490
title: `قیمت ${sub.label} امروز | بنیان فولاد داریا`,
description: `قیمت روز ${sub.label} از کارخانه‌های معتبر کشور. استعلام قیمت، مشخصات فنی و درخواست پیش‌فاکتور ${sub.label} با مشاوره تلفنی بنیان فولاد داریا.`,
```

Rendered audit:

```text
indexable routes:                         66
duplicate literal titles:                 0
duplicate literal meta descriptions:      0
subcategory titles matching one skeleton: 44/44
subcategory descriptions one skeleton:    44/44
```

To quantify page-body repetition, I extracted visible leaf text blocks from `<main>`, normalized whitespace/ZWNJ, replaced numeric runs with `#` so changing prices would not masquerade as editorial uniqueness, and called a block boilerplate when it appeared in at least half the pages of the same template group. Ratio = unique characters / (unique + boilerplate characters):

| Template group | Pages | Unique-text ratio | Median | Lowest examples |
|---|---:|---:|---:|---|
| Family landing | 8 | 29.1%–60.1% | 40.9% | `/sheet/` 29.1%; `/pipe/` 32.4%; `/wire/` 34.2% |
| Subcategory | 44 | 11.6%–32.3% | 22.3% | `/sheet/oily-sheet/` 11.6%; `/rebar/alloy/` 13.5%; `/profile/box-profile/` 15.6%; `/rebar/stainless/` 16.5% |

These ratios are deliberately conservative but not a Google quality score: price tables, controls, and repeated commercial disclaimers are legitimate. The concern is that factory, grade, dimension, standard, unit, and buyer-intent differences are mostly carried by tables rather than page-specific explanatory copy and metadata.

Pixel-width audit used the actual loaded Vazirmatn font, not English character-count rules. Assumptions were 20 px/600 weight for title text with a 600 px review band and 14 px/400 for descriptions with a 920 px review band. Google has no fixed title or description character limit; truncation depends on device width, so these are explicit audit bands rather than ranking limits.

```text
title widths:       min 203 px; median 334 px; max 590 px; >600 px = 0
description widths: min 509 px; median 805 px; max 896 px; >920 px = 0
widest title:       /guide/units-and-quote-specs/ (590 px)
widest description: /guide/ipe-vs-hash-beam/ (896 px)
```

Google recommends descriptive, concise, non-boilerplate title text and page-specific descriptions; it also notes that programmatic descriptions are appropriate when they use page-specific data: [Title links](https://developers.google.com/search/docs/appearance/title-link), [Snippets](https://developers.google.com/search/docs/appearance/snippet).

#### Mechanism of harm

- **Rank/relevance:** many pages give search systems little prose beyond the entity name and structured table values to distinguish intent.
- **Search presentation:** near-identical title/description patterns give Google less page-specific summary material and may be rewritten.

No search-volume or ranking claim is made.

#### Proposed fix

Generate or author concise page-specific copy from already validated facts: product form/grade, standards, available dimensions, real producers/groupings, unit semantics, and how to request a quote. Keep price data and factual claims sourced; do not invent advantages, standards, inventory, or producer relationships. Prioritize the lowest-ratio subcategories and the search-query evidence supplied by Search Console.

#### Verification after implementation

Rebuild and compare literal/template similarity, normalized unique-text ratios, pixel widths, H1/entity coverage, and snapshot tests. Review the rendered Persian copy for factual consistency with the catalog and confirm Search Console query/page CTR trends only after deployment.

### F05 — LightPillar has a measurable mobile LCP and main-thread cost

**Classification:** verified performance cost; changing the visual is a judgment call.  
**Severity:** Medium.  
**Risk:** higher-risk visual/performance change.

#### Evidence

The mobile tier still ray-marches 24 iterations at 30 fps (`app/LightPillar.tsx:9-30`). Each instance creates and compiles its own WebGL2 canvas/program and starts a `requestAnimationFrame` loop:

```tsx
// app/LightPillar.tsx:263-326 (excerpt)
canvas = document.createElement("canvas");
gl = canvas.getContext("webgl2", { ... powerPreference: "low-power" });
program = createProgram(gl, fragmentShader(tier));
// ... buffers and uniforms ...
render((performance.now() - globalClockStart) * 0.001 * 0.15);
startOrStopLoop();

// app/LightPillar.tsx:239-260 (excerpt)
const animate = (...) => {
  if (delta >= frameTime) render(...);
  frame = requestAnimationFrame(animate);
};
```

Two instances occur above the main content in `app/SiteHeader.tsx:75-80` and `app/SiteHeader.tsx:136-138`; a third footer instance is below the viewport (`app/SiteFooter.tsx:36-42`).

Three interleaved live A/B runs on `/rebar/ribbed/` used the same mobile profile described in F02. The “off” condition disabled WebGL2 before page script execution while preserving the rest of the app:

| Metric (median of 3) | LightPillar on | WebGL2 off | Difference |
|---|---:|---:|---:|
| LCP | 2,744 ms | 2,484 ms | **+260 ms** |
| Total traced task duration | 4,685 ms | 4,456 ms | **+229 ms** |
| Script task duration | 951 ms | 856 ms | **+95 ms** |
| Long-task duration total | 1,330 ms | 1,125 ms | **+205 ms** |
| Sampled mobile-nav interaction max duration | 64 ms | 72 ms | no measured regression |

The LCP element in every A/B run was the responsive `<img>` hero (`hero-rebar-960.avif`), not the canvas. LightPillar delays its paint indirectly through CPU/main-thread contention. A same-machine local static-server A/B corroborated directionally smaller costs: +44 ms median LCP, +145 ms task time, +68 ms script time, and +75 ms long-task time; local absolute timings were inflated because Python's static server did not reproduce Cloudflare compression.

The sampled click timing is **not** an INP score. INP is a field distribution over a page visit, evaluated at the 75th percentile; one automated interaction can only show that this particular event was not slower with the pillar enabled. Field INP is listed under external data.

#### Mechanism of harm

- **Render:** WebGL setup/shader compilation and two animation loops compete with hydration and hero decoding during LCP.
- **Interaction:** a cost exists on the main thread, although this audit did not measure an INP regression.

#### Proposed fix

Run a visual-preserving experiment: initialize the header effect after LCP/idle, share one canvas between the two header bands, or use a static/mobile fallback on constrained devices. Preserve reduced-motion behavior. Do not remove the visual without design review.

#### Verification after implementation

Repeat the same interleaved A/B protocol and require a repeatable LCP/main-thread improvement without increasing CLS or the sampled interaction duration. Inspect all three viewports and both motion preferences. Confirm field LCP/INP later through CrUX or RUM.

### F06 — Article structured data omits `datePublished`

**Classification:** deviation from documented best practice.  
**Severity:** Low.

#### Evidence

All five guide articles emitted valid JSON with `Article`, `headline`, `description`, image, `inLanguage`, `dateModified`, author, and publisher. None emitted `datePublished`:

```js
// scripts/lib/prerender-pipeline.mjs:169-203
const payload = {
  "@context": "https://schema.org",
  "@type": "Article",
  mainEntityOfPage: { "@type": "WebPage", "@id": pageUrl },
  headline,
  description,
  ...(image ? { image: [image] } : {}),
  inLanguage: "fa",
  dateModified: lastmod,
  author: { "@type": "Organization", ... },
  publisher: { "@type": "Organization", ... },
};
```

Rendered inventory:

```text
JSON-LD objects: 73 across 66 indexable pages
JSON parse errors: 0
Article objects: 5
Article objects missing datePublished: 5
```

Google lists `datePublished` as a recommended Article property, not a required property: [Article structured data](https://developers.google.com/search/docs/appearance/structured-data/article). This is therefore not a rich-result eligibility defect.

#### Mechanism of harm

- **Search presentation:** an explicit publication date gives Google another supported signal for date interpretation. Its absence does not prevent Article eligibility.

#### Proposed fix

Add `datePublished` only from a truthful, durable first-publication source. Do not copy `dateModified` or invent dates to fill the property.

#### Verification after implementation

Parse every emitted JSON-LD block, validate ISO dates, confirm visible article dates agree, and test representative guide URLs in Google's Rich Results Test after deployment.

### F07 — Precise Organization address is not visibly corroborated on marked-up pages

**Classification:** judgment call informed by documented structured-data policy.  
**Severity:** Low.

#### Evidence

Rendered JSON-LD inventory found `Organization` on `/` and `/about/`, and `WebSite` on `/`. Exact-string comparison found the structured `streetAddress` on neither page's visible text. The exact address does appear on the dedicated contact page, but that page does not carry the Organization object.

```text
Organization objects:                         2  (/, /about/)
exact streetAddress visible on those pages:   0/2
JSON parse errors:                             0
```

The current generator deliberately places Organization data on those two routes:

```js
// scripts/lib/prerender-pipeline.mjs:399-421,524-537
const organizationData = buildOrganizationStructuredData();
// homepage descriptor
organizationData,
// info page descriptor
organizationData: slug === "about" ? organizationData : null,
```

Google's general policy says structured data should be a true representation of the page and should describe content visible to users: [Structured data guidelines](https://developers.google.com/search/docs/appearance/structured-data/sd-policies). An Organization entity can legitimately be site-level, so this is a conservative warning rather than a verified violation.

#### Mechanism of harm

- **Rich-result trust/eligibility:** a validator or reviewer may regard precise details as insufficiently corroborated on the marked-up URL.

#### Proposed fix

Either add a concise visible address/contact reference to the marked-up Organization context, or put the Organization object on the contact page and link it consistently by `@id`. Keep central company data as the single source of truth.

#### Verification after implementation

Compare JSON-LD values against visible text and `siteConfig`, parse every built object, and run the live URL through Rich Results Test/Schema Markup Validator. Verify no factual field was changed merely for markup convenience.

The Product/Offer decision has an additional currency constraint: UI market prices are toman, while quote documents convert totals to rial (`CONTEXT.md:71-73`). `priceCurrency` expects an ISO 4217 code; IRR is available, IRT is not. Price-route `dateModified` is currently expressed through sitemap dates, not a WebPage/Product JSON-LD object. Fixing F01 is a prerequisite; adding structured freshness to stale artifacts would only make the contradiction more explicit.

## 4. Requires external data

These questions cannot be answered scientifically from the repository, local build, or one live diagnostic crawl:

1. **Root cause of stale production prices:** GitHub Actions run history/logs for “Refresh prices (Cloudflare relay)”; Worker `/status` record and Worker logs; presence/value status (not secret contents) of `PRICE_DATA_ENDPOINT`, `PRICE_INGEST_TOKEN`, and `DEPLOY_HOOK_URL`; deploy-hook responses; Cloudflare Pages deployment/build logs and deployed commit IDs.
2. **Actual Google indexing/canonical choices:** Search Console Pages report, submitted-sitemap history, and URL Inspection for representative family, subcategory, query-filter, redirect, and 404 URLs.
3. **Queries and entity priorities:** Search Console Performance export by query and page. This is required before claiming which producer/grade/dimension wording has demand; no search volumes were invented here.
4. **Crawl waste from filters:** Cloudflare request logs or another server-log export filtered to verified Googlebot traffic, including query strings, status, bytes, and timestamp. Search Console crawl statistics alone are less granular.
5. **Field Core Web Vitals:** CrUX/Search Console Core Web Vitals or first-party RUM at the 75th percentile, segmented by mobile template. This is necessary for real LCP, CLS, and especially INP; the lab click in F05 is not INP.
6. **Organic outcomes:** Search Console clicks, impressions, position, and CTR before/after changes. GA may help with user behavior/conversion but cannot prove ranking impact.
7. **Google's deployed structured-data interpretation:** Rich Results Test and URL Inspection rendered HTML for representative live URLs after any markup change. Local JSON parsing cannot report live Google eligibility or manual actions.
8. **Full live crawl history/edge variance:** a scheduled crawl from target geography plus Cloudflare edge logs. This audit sampled the current live host successfully but did not fabricate a global/CDN-wide result.

If local tooling becomes available, the preferred repeatable run is Lighthouse or Unlighthouse against the built site plus a separate live edge sample. In this environment the exact availability check returned no installed `lighthouse`, `@unlighthouse/cli`, or `playwright`; browser instrumentation therefore used the already installed Chrome and documented profile above.

## 5. Proposed Phase 2 sequencing

Each item should remain an independent concern/review unit. “PR” here is sequencing only; no PR or change was created in Phase 1.

1. **Restore price freshness and add an SLA guard — Critical, higher-risk price-data pipeline.** First obtain the external logs in item 1 above. Then fix only the failing relay/KV/hook/Pages seam and add monitoring. Preserve validation and atomic snapshot publication.
2. **Stabilize the market-widget footprint/auto-scroll — High.** One layout/behavior change with success, failure, blocked, and slow API tests; require lab CLS ≤ 0.1.
3. **Contain `factory`/`size` crawl space — Medium.** Change only filter navigation/crawl policy, with graph and UI regression tests.
4. **Differentiate page metadata and explanatory copy — Medium.** Start with the lowest-ratio subcategories; use only validated catalog/domain facts and Search Console evidence.
5. **Optimize LightPillar startup — Medium, higher-risk visual system.** Treat as an A/B performance and visual-parity change; avoid combining it with CLS or metadata work.
6. **Structured-data polish — Low.** Add truthful article publication dates and resolve Organization visibility/placement. Keep Product/Offer as a separately approved business/URL-model decision, not part of routine schema cleanup.

## 6. Explicitly out of scope for an agent

- Backlink acquisition, digital PR, publisher relationships, and reputation building.
- Real-world E-E-A-T improvements such as author credentials, company certifications, independent reviews, organizational history, licenses, or business claims that do not already have verified source material.
- Deciding whether a non-binding market-reference row legally or commercially constitutes an `Offer`.
- Creating search demand, guaranteeing rankings, or predicting traffic/revenue uplift.
- Search Console/manual-action decisions, Google-selected canonicals, and field Core Web Vitals without account/log access.
- Changing business operations, sales response quality, stock accuracy, source contracts, or the upstream publisher's data quality.

Code changes can improve crawl efficiency, rendering stability, freshness delivery, semantic clarity, and eligibility signals. They cannot substitute for current source data, real-world authority, demand, or external reputation.
